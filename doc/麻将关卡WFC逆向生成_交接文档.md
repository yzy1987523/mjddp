# 麻将对对碰 · 关卡逆向生成（WFC 方案）交接文档

> 版本：v1.0
> 状态：方案已定型，代码为可运行原型（HTML+JS）
> 适用读者：接手该关卡生成模块的开发 / 策划

---

## 一、项目背景与目标

### 1.1 要解决的问题
麻将「对对碰」类消除游戏需要**自动生成关卡**。生成的关卡必须满足两个硬性要求：

1. **可通关**：从生成好的棋盘上，存在一条按「消除规则」一步步消掉全部牌的路径（正向可解）。
2. **布局合理**：棋盘盒子堆叠骨架固定，牌的摆放自然、连片、不零散，符合人工摆牌的观感。

### 1.2 核心思路（一句话）
**逆向构造**：不是"先生成棋盘再求解"，而是**从空棋盘往盒子里放牌**。放牌的每一步都遵守「消除规则的反向约束」，放完所有牌后，**把放置顺序反转，就天然得到一条保证通关的消除路径**，无需再搜索求解。

> 正向消除顺序 = 逆向放置顺序的完全反转
> 最后放上的牌（层级最高）开局即可点，逐层消到最早放的牌。

## 二、核心概念定义

### 2.1 盒子骨架（Skeleton）
- 固定的堆叠容器集合，**位置与上下左右邻接关系预先写死，生成过程中不变**。
- 每个盒子最多放 **1 张牌**。

盒子数据结构（JS 伪码）：
```js
class Box {
  id;                // 唯一ID
  row;               // 行号
  gx;                // 行内网格横坐标
  underBoxList;      // 所有被它压住的下层盒子（数组，空=落在地面）
  leftBox;           // 左侧盒子
  rightBox;          // 右侧盒子
  segment;           // 归属的行分段
  hasCard;           // 是否已放牌
}
```

### 2.2 行分段（Segment）
- **空位**：同一行内两个相邻盒子之间没有盒子，即为空位。
- **分段**：同一行里**连续相邻、中间没有空位**的一组盒子；遇到空位即切断，开启新分段。
- 每个盒子归属唯一分段。

示例：
```
盒子A 盒子B (空位) 盒子C 盒子D 盒子E
分段1: [A,B]    分段2: [C,D,E]
```

### 2.3 对子（Pair）
- 两张相同牌组成一对。生成时，牌的类型成对出现，一对牌分到**两个不同盒子**。

## 三、放牌规则（三条，全部生效）

放置一张牌到盒子前，该盒子必须**同时满足**以下全部规则：

### 规则 1：底部支撑
盒子底部要么是**地面**，要么**所有被它压住的下层盒子都已放牌**。

### 规则 2：左右约束
盒子**左右两个盒子最多只能有一侧有牌**，禁止左右两侧同时有牌。
- 可放：左有右无 / 左无右有 / 左右皆无
- 禁放：左右同时有牌

> 候选优先级：在所有满足规则的候选中，**优先选择「一侧已有牌」的盒子，其次才是「左右都为空」的盒子**。

### 规则 3：分段生长（连片）
以行分段为单元：
- 若分段内**已存在至少一张牌**：新牌必须**紧贴**该分段内任意一张已有牌（左右直接相邻）。
- 若分段内**一张牌都没有**：本规则不生效，该分段内满足前两条规则的盒子都可选。

> 紧贴只看**同分段内左右相邻**；上下层的牌不算紧贴；不同分段间有空位隔离，互不干扰。

### 规则总结表
| 规则 | 内容 | 作用 |
|---|---|---|
| 1 底部支撑 | 下方是地面 / 所有下压盒子都有牌 | 保证层级支撑合法 |
| 2 左右约束 | 左右最多一侧有牌（优先单侧已有） | 避免中间盒子被锁死 |
| 3 分段生长 | 分段有牌时新牌必须紧贴已有牌 | 牌连片生长，不零散孤立，进一步降低死局概率 |

## 四、算法选型：为什么用 WFC（波函数塌缩）

### 4.1 备选方案对比
| 方案 | 性能 | 卡死风险 | 实现复杂度 | 适配成对牌约束 |
|---|---|---|---|---|
| 贪心 + 边缘优先 | 最优 | 中等，后期易锁死盒子 | 低 | 简单 |
| **WFC（本方案）** | 很好，远优于暴力回溯 | 低，偶尔冲突整局重跑 | 中 | 需额外管理全局对子池 |
| 纯 DFS 回溯 | 差，盒子一多指数爆炸 | 零（只要骨架可行必找到解） | 高 | 容易 |

### 4.2 为什么选 WFC
1. **性能**：WFC 每次优先塌缩「熵最低（可选状态最少）」的盒子，**提前啃硬骨头**，约束传播一次性批量修剪无效选项，平均速度远快于暴力回溯，避免了深度回溯的指数级分支爆炸。
2. **天然化解死局**：那些「即将被左右填满、马上锁死」的中间盒子可选状态最少、熵最低，会被优先处理，而不是留到最后没得选——正好命中贪心方案后期锁死中间盒子的痛点。
3. **声明式约束**：三条放牌规则都能编码进约束传播，规则后续改动方便。

### 4.3 WFC 的局限与应对
- 原生 WFC 只擅长**单格子局部邻接约束**，不支持「成对牌」这类**全局计数约束**。
- **应对：两阶段分离**（见下节），把「空间占位生成」和「卡牌配对」拆开，规避该局限。

## 五、两阶段生成流程（核心架构）

### 阶段一：WFC 生成合法占位（哪些盒子放牌）
- WFC 只决定每个盒子的状态：`empty`（空）或 `hasCard`（放牌）。
- 约束传播阶段，每个盒子塌缩/校验时依次检查规则 1、2、3。
- 全部盒子塌缩完毕 → 得到合法的 `hasCard` 盒子集合。
- 若某盒子可选状态归零（矛盾冲突）→ 本轮作废，**整局重跑 WFC**（可重试 N 次）。

### 阶段二：成对卡牌分配（往占位盒子里放对子）
- 拿到阶段一输出的全部 `hasCard` 盒子列表。
- 数量必须为偶数（否则警告并放弃该局）。
- 构建麻将对子池（成对卡牌），洗牌后分配到这些盒子，保证一对两张落在不同盒子。
- 盒子的合法占位已由阶段一保证，此阶段只需保证同对分盒。

### 流程示意
```
骨架定义 → 预处理分段/邻居 → [WFC 阶段一] 生成 hasCard 占位
        → 合法?  → [阶段二] 对子分配 → 输出关卡
        → 冲突?  → 整局重跑 WFC（重试 N 次）
```

## 六、WFC 算法细节（JS 伪码）

### 6.1 盒子可放置校验（三条规则合体）
```js
function canPlaceCard(box, stateMap) {
    // 规则1：所有下压盒子必须已放牌
    for (const u of box.underBoxList)
        if (stateMap[u.id] !== "hasCard") return false;

    // 规则2：左右不能同时有牌
    const leftHas  = box.leftBox  && stateMap[box.leftBox.id]  === "hasCard";
    const rightHas = box.rightBox && stateMap[box.rightBox.id] === "hasCard";
    if (leftHas && rightHas) return false;

    // 规则3：分段紧贴约束
    const seg = box.segment;
    const segHasCard = seg.boxes.some(b => stateMap[b.id] === "hasCard");
    if (segHasCard) {
        const adjacent = (box.leftBox && stateMap[box.leftBox.id] === "hasCard")
                      || (box.rightBox && stateMap[box.rightBox.id] === "hasCard");
        if (!adjacent) return false;
    }
    return true;
}
```

### 6.2 WFC 主循环
```js
// 每个盒子一个叠加态单元
class WfcCell {
    box;
    possible = ["empty", "hasCard"]; // 可选状态
    get entropy() { return this.possible.length; }
}

while (存在未塌缩单元) {
    // 1. 选熵最低（可选状态最少）的盒子优先塌缩
    const target = getLowestEntropy(uncollapsedCells);
    // 2. 塌缩：随机选定 empty / hasCard
    target.possible = [randomPick(target.possible)];
    state[target.box.id] = pickState;
    // 3. 约束传播：刷新所有未塌缩单元，剔除违反三条规则的选项
    propagate();   // 逐单元用 canPlaceCard 过滤
    // 4. 检测矛盾
    if (某单元 possible 为空) { hasConflict = true; break; }
}
if (hasConflict) { 重置全部状态，重新跑WFC（重试） }
```

### 6.3 骨架与分段预处理
- 按 `row` 分组，行内按 `gx` 排序。
- 遍历：若 `gx === prev.gx + 1` 归入当前分段，否则开启新分段。
- 给每个盒子绑定 `segment`，并填充 `underBoxList`、`leftBox`、`rightBox`。

## 七、可运行原型（代码结构说明）

交付物为单文件 HTML（内联 CSS/JS），包含：
- 固定盒子骨架定义（`skeletonRaw` 数组，含 `row/gx/under`）
- 分段自动预处理
- WFC 生成器（`runSingleWFC`，含重试机制）
- 对子分配（`assignPairs`）
- Canvas 可视化渲染（盒子、分段、卡牌编号）
- 日志面板

### 关键函数清单
| 函数 | 职责 |
|---|---|
| `initSkeleton()` | 构建盒子、填充邻居/下压/分段 |
| `canPlaceCard()` | 三条规则合体校验 |
| `runSingleWFC()` | 单次 WFC 运行，冲突返回 null |
| `runWFCGenerate()` | 生成入口，带 N 次重试 |
| `assignPairs()` | 对子卡牌分配 |
| `redraw()` | Canvas 渲染 |

### 可扩展点
1. 修改 `skeletonRaw` 自定义盒子堆叠布局（增删盒子、改 under 依赖）。
2. 调整重试上限 `maxRetry`（骨架越复杂成功率越低，可调高）。
3. 后续可加「正向消除自动验证」模块，生成后立刻按消除路径跑一遍通关测试。

## 八、测试与验证

### 8.1 已验证的约束完整性
生成时三条规则全部内置，通过 `canPlaceCard` 在约束传播阶段逐盒校验。

### 8.2 建议的验收项
1. **合法性**：生成的 `hasCard` 集合，每个盒子逐条满足规则 1/2/3。
2. **成对性**：可放牌盒子数为偶数，所有牌可配成整对。
3. **可解性（最重要）**：正向按「消除规则」跑一遍，能消掉全部牌（当前原型尚未内置正向验证，属待补项）。
4. **成功率**：统计 WFC 重试次数分布，确认在目标骨架下能在有限重试内成功。
5. **观感**：分段内牌是否连片生长、无孤立散点。

### 8.3 已知边界与坑
- **盒子数量非偶数**：阶段二会失败，需在阶段一后判断并放弃/重跑。
- **WFC 冲突**：属于正常现象，靠重试解决；若重试耗尽仍失败，说明骨架本身可能偏紧，需调整骨架或放宽约束。
- **成对全局约束**：WFC 本身不管，必须在阶段二单独处理，否则会出现对子数量不匹配。

## 九、后续优化方向

1. **正向消除自动验证模块**：生成后立即自动跑通关测试，双保险验证可解性。
2. **WFC + 局部回溯（Tessera 式）**：塌缩时存快照，冲突只回退最近几步而非整局重跑，提升成功率与速度。
3. **骨架预校验**：生成前评估骨架理论可放盒子数，小于目标直接换骨架，减少无效重试。
4. **失败次数与骨架紧度的自动诊断**：输出冲突发生位置，辅助调整骨架布局。
5. **性能压测**：在目标盒子规模（几十~上百）下，统计单局生成耗时与重试率。

## 十、交接注意事项（给接手人）

- 本方案的关键是**逆向构造 + 两阶段分离**：空间占位（WFC）与卡牌配对（阶段二）解耦，便于各自独立演进和调优。
- 三条规则的顺序是硬约束：阶段一 `canPlaceCard` 必须**同时**满足三条，少一条都会导致生成的布局与正向消除规则不一致，出现不可解关卡。
- 若后续修改规则，务必同步修改 `canPlaceCard` 和阶段二的校验逻辑，避免「生成规则」与「消除规则」脱节。
- 原型为 JS 原型，正式接入游戏引擎（Unity/Godot 等）时，将三段（骨架定义、WFC、对子分配）按引擎语言移植，逻辑保持不变。
